Chapter 1: System design thinking

Everything we worked through in Chapter 1: how to turn "it should be fast and cheap" into defensible numbers for memory, throughput, fleet size and monthly cost. The Calculator tab runs the same math live.

1. How LLM systems differ from classical ML

PropertyWhat it means for the design
Cost is per tokenPlan capacity in tokens/second, not queries/second. One turn can cost 1,000× another.
Latency is sequentialOutput is generated one token per step. A 1,000-token answer is 1,000 small computations.
Memory is stateful per requestThe KV cache grows with sequence length and caps concurrency on a GPU.
Quality is open-endedNo single accuracy number. You need LLM judges, human review and online metrics.

The five dimensions you trade against each other: latency (TTFT and time to last token), throughput, cost, quality, and safety (a hard constraint, not a trade-off).

2. KV cache estimation

What the KV cache is

To generate token #501 the model attends to all 500 earlier tokens. Each token gets a Query, a Key and a Value vector. A token's K and V never change once computed, so the engine stores them in GPU memory instead of recomputing them every step. That store is the KV cache. It trades memory for compute, much like Flink keyed state or an incrementally maintained view.

Worked example (Llama 3 8B shape, 4K context, 80 GB GPU)

KV/token     = 2 × 32 × 8 × 128 × 2   = 131,072 B ≈ 128 KB
Per request  = 128 KB × 4,096 tokens  = 0.5 GB
Usable       = 80 GB − 16 GB weights  = 64 GB
Concurrency  = 64 ÷ 0.5               = 128 requests per GPU

Weights are a fixed cost shared by everyone. KV is a per-request cost. Whatever memory the weights leave decides how many requests run at once, which is why the book calls KV "the real concurrency limit".

Why KV heads matter: MHA → GQA → MQA

Only KV heads are cached; query heads are needed only for the current token. Sharing K/V heads across query heads (GQA) shrinks the cache directly.

Details in the code

hidden_size is accepted but never used. The old formula 2 × L × hidden_size × b is only right for MHA; with GQA it overestimates by 4×. GPU memory is in vendor GB while KV uses GiB. The estimate also ignores activations and engine overhead (vLLM reserves ~90%), assumes every request uses the full context, and assumes perfect packing (PagedAttention in Ch. 9 gets close). Treat 128 as an upper bound.

A replica is not always one GPU. If the weights plus KV room don't fit on one GPU, the model is split across several (tensor parallelism) and those GPUs act as one replica.

total GPUs = replicas × GPUs per replica. The book's "179 replicas" is 179 GPUs only if each replica is one GPU.

4. Batching and its gaps

Each decode step reads all the weights from GPU memory. That read is the slow part, and once done it can be applied to many requests at almost no extra cost. So engines run a batch: one step produces one token for every request in it. A replica's output rate is batch size × steps per second. An empty slot is lost throughput.

Requests finish at different times

Static batching (batch waits for the longest request)
Slot 1  A █░░░░░░░░░░░░░░░   A: 50 tokens
Slot 2  B ████░░░░░░░░░░░░   B: 200 tokens
Slot 3  C ████████████████   C: 800 tokens
Slot 4  D ██░░░░░░░░░░░░░░   D: 100 tokens
Useful 1,150 of 3,200 slot-steps = 36% utilization

Continuous batching (vLLM, TGI): a freed slot is refilled at the next step
Slot 1  A █E█████F█████████
Slot 4  D ██J██████K███████

Gaps that remain even with continuous batching

  1. Nobody waiting. A slot frees during a traffic lull.
  2. Prefill stalls. A new request must process its whole prompt first, slowing the rest of the batch.
  3. Free slot, no memory. The KV pool is full, so the scheduler can't admit anyone.
  4. Operations. Restarts, deploys, warm-up and draining.

The Spark parallel: stragglers hold a stage open while executors sit idle.

5. Headroom: bursts, gaps and p99 tails

effective = per_replica_tokens_per_sec × utilization     # 40 × 0.7 = 28
replicas  = ceil(target_tokens_per_sec / effective)      # ⌈5000/28⌉ = 179  (vs 125 at 100%)
  • Bursts. Traffic arrives randomly. A fleet sized at exactly the average builds a backlog on every spike and can't drain it, like Kafka consumer lag. Predictable daily peaks are a separate adjustment (the ~3× peak factor).
  • Batching gaps. The benchmark peak assumes an always-full batch. Production never sustains it.
  • p99 tails. Queue wait grows like 1/(1−ρ). Past ~75–80% busy, small load increases cause huge latency increases.
  • Failure headroom. Losing a zone shouldn't take everything down.
Utilization ρ50%70%80%90%95%99%

6. Monthly cost and caching

billable = requests_per_day × (1 − cache_hit_rate)
per_req  = in/1000 × $in_per_1k + out/1000 × $out_per_1k
monthly  = billable × per_req × 30

A cache hit in this function skips the whole model call, so it costs $0. That models a response or semantic cache: paraphrases of the same question ("reset my password", "forgot password, help") land close together in embedding space and reuse a stored answer.

CacheStoresA hit saves
Response / semanticFinal answersThe entire call
Prompt / prefix (provider)KV of a shared prompt prefixInput tokens get much cheaper; output still billed
KV cacheK/V inside a running requestRecomputation. GPU memory, not billing

Cost of a semantic cache: an embedding call and a vector lookup on every request, staleness (needs a TTL), and false hits that return a wrong answer. Chapter 32 tunes the similarity threshold.

7. Bigger replicas vs. more replicas

Total KV memory = total GPU memory − (replicas × weights). Fewer, bigger replicas hold fewer weight copies. The gain is large when weights crowd each GPU and small otherwise.

Llama 3 70B on 8 GPUsKV leftTotal slots (4K)
4 replicas × TP=280 GB64
2 replicas × TP=4360 GB288
1 replica × TP=8500 GB400

For an 8B model the same move gains only 12–22%. The costs of bigger replicas: an all-reduce after every layer (keep TP inside one NVLink node), more slots you may not be able to fill, bigger batches that slow every user, a larger blast radius, and autoscaling in coarse steps. The benefit: lower per-token latency and one shared slot pool.

Rule of thumb

Use the smallest TP that fits the weights, leaves KV for the batch you actually need (Little's Law), and meets per-user latency. Then scale out with replicas.

8. The estimation chain, worked

req/day → tok/s → replicas → $/month. Scenario: an internal support assistant with 2M requests/day, 1,500 input and 400 output tokens, and a 3× peak.

Peak output  = 2M × 400 ÷ 86,400 × 3   ≈ 27,778 tok/s
Peak input   ≈ 104,167 tok/s ;  peak requests ≈ 69.4 req/s

Path A: API (Claude Sonnet 5.5 at $2 / $10 per M, $0.20 cached)

Input   90B tok × $2/M  = $180,000
Output  24B tok × $10/M = $240,000      → $420,000 / month
+ prompt cache (1,000-token system prompt)  → $312,000
+ semantic cache, 25% hit                  → $234,000
Rate limits: ~1.67M output and ~6.25M input tokens per minute at peak

Path B: self-host Llama 3.1 405B (FP8, one 8×H100 node per replica)

KV/token     = 2 × 126 × 8 × 128 × 2 ≈ 504 KB ;  per request (1,900 tok) ≈ 0.91 GB
Slots        = (640 × 0.9 − 405) ÷ 0.91 ≈ 187 per replica
Replicas     = ⌈27,778 ÷ (2,000 × 0.7)⌉ = 20   (2,000 tok/s per replica is an assumed load-test figure)
GPUs         = 20 × 8 = 160 H100
Little's Law = 69.4 req/s × 13.8 s ≈ 961 in flight → 48 per replica of 187 → throughput-bound
Cost         = 160 × 720 h × $4.25 ≈ $489,600  (AWS p5 at $6.88 ≈ $792,576)

Self-hosting loses here because the fleet is sized for peak but billed 24/7. The break-even is utilization. The two models are also not equal in quality, so set the quality bar first.

9. Q1.1: Size the fleet for a chat assistant

1M conversations/day, 800 input and 300 output tokens each, p95 end-to-end latency ≤ 2 s.

The book's answer

Output rate  = 300M ÷ 86,400 ≈ 3,472 tok/s ;  peak ×3 ≈ 10,000 tok/s
Replicas     = ⌈10,000 ÷ (40 × 0.7)⌉ = 358
KV check     = 1,100 tok × 128 KB ≈ 0.13 GB/request → not memory-bound
Latency      = TTFT (queue + prefill) + 300 decode steps ; stream tokens
Cost         = semantic cache + route easy turns to a small model

What it glosses over

At 40 tok/s per user, 300 tokens take 7.5 s, which violates the 2 s SLO. And Little's Law gives 34.7 req/s × 2 s ≈ 70 requests in flight across all 358 replicas, which is 0.2 per GPU. The 40 tok/s is one request's speed, not a batching replica's total output.

Corrected approach

Clarify      2 s for first token or full answer? conversation = 1 turn? model size?
Required     (2.0 − 0.3 s TTFT) → 300 ÷ 1.7 ≈ 176 tok/s per user (≤ 5.7 ms per step)
Load test    largest batch still ≥ 176 tok/s per user, e.g. 16 → 2,880 tok/s per replica
Replicas     ⌈10,417 ÷ (2,880 × 0.7)⌉ = 6 ; with N+1 across 2 zones ≈ 8
Check        96 slots vs ~70 needed ≈ 73% ; KV ≈ 2 GB of 64 GB
Cost         358 GPUs ≈ $1.1M/month vs 8 GPUs ≈ $24K/month

The batch-16 figures are illustrative. The method is to let the latency SLO pick the batch size, then size replicas.

10. Q1.3: "Too expensive" at $120K/month

Before changing the model, what is your diagnostic process?

COST = Volume × Tokens × Price × (1 − cache hit rate)
  1. Define. Too expensive relative to what? Get the unit cost per request, user or resolved ticket.
  2. Instrument. Log input tokens, output tokens, model, cache outcome, feature and calls per user action.
  3. Decompose. 500K req/day × (2,500 in, 300 out) at $2/$10 = $0.008/request = $120K. 63% input, 37% output, 0% cache.
  4. Find waste. Bloated prompts and RAG context, unbounded output, no cache, one big model for everything, agent loops or retries.
  5. Quantify each lever. Model it with monthly_inference_cost before changing production.
  6. Change the model last. It's the only lever that removes capability rather than waste.
LeverMonthlySaved
Baseline$120,000—
Trim input 2,500 → 1,500$90,000−25%
Cap output 300 → 250$82,500−8%
Semantic cache, 30% hit$57,750−30%
Cascade 60% to a small model (1/10 price)$26,565−54%

Guardrail: run the eval harness after each change. Trimming can drop the needed chunk, caps can truncate answers, the cache can return false hits, and the cascade can answer when it should escalate.

11. Q1.5: p99 jumps 1.8 s → 9 s while GPU utilization drops

What is your hypothesis and how do you confirm it?

Design lesson

Alert and autoscale on KV occupancy, queue depth and TTFT. GPU utilization can fall exactly when the system is in the most trouble.

12. Errata found in the book

  • Page 6 cost example: 1M requests/day, 800 in / 256 out at $0.012/1K, 30% hit is stated as ~$115K/month. monthly_inference_cost returns $266,112, and the arithmetic agrees.
  • Per-replica 40 tok/s: used as replica throughput in gpus_for_throughput, but it's a single request's decode speed. With batching a replica produces many times that.
  • Q1.1: 40 tok/s per user can't meet a 2 s end-to-end SLO for 300 tokens. The answer reinterprets the SLO as TTFT via streaming without saying so.
  • kv_cache_memory: the hidden_size parameter is unused (correctly, for GQA models).
